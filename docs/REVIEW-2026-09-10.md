# Application review — 10 September 2026

The application passes its existing verification suite, but eight actionable defects remain. The most urgent are numeric input corruption and acceptance of physically invalid PPFD through study JSON. This review did not modify application code.

## Repair follow-up

All eight code defects below were subsequently addressed in version 0.1.1, with regression tests. Supporting rendering, sensor labeling, mobile navigation, keyboard accessibility, progress reporting and CI improvements were also implemented. See [current status](STATUS.md) and [repair notes](REVIEW-FIXES.md). The original findings and reproductions below are retained as the historical review; independent physical/field validation remains a release gate.

## Confirmed findings

### 1. [P1] Numeric fields corrupt ordinary keyboard entry

**Location:** `src/ui/Controls.jsx:55–59` (`Field`), with immediate schema validation in `src/main.jsx`.

**Reproduction:** In the real browser, select the existing `0.2` in a sensor's Height / depth field and type `-0.15` character by character. The resulting value was **0.2015**, not −0.15. The original 0.2 value was restored after the test.

The controlled input immediately converts every valid intermediate value to a number, while refusing empty or incomplete numeric strings. Typing a minus sign or decimal prefix therefore restores the old value; later digits can append to it. Immediate minimum validation also interferes with replacing positive dimensions with fractions. This affects installation depths, coordinates and geometry, and the unintended value is saved automatically.

**Fix:** Keep a local string while editing. Parse, validate and commit on blur/Enter, preserving incomplete input until then. Show validation beside the field. Add real keyboard tests for negative numbers, decimal fractions, clearing, replacement and invalid commits; whole-value `fill()` tests do not expose this bug.

### 2. [P1] Study JSON bypasses physical PPFD validation

**Location:** `src/domain/study.js:94–102`; `src/irradiance/engine.js:84–104`.

CSV import checks that diffuse PPFD requires total PPFD and cannot exceed it. The authoritative Study schema only bounds each number independently, and the engine does not repeat the relational check. A JSON study with total PPFD = 100 and diffuse PPFD = 200 is accepted.

**Reproduction:** Assign those values to illuminated intervals of a complete synthetic day, set upload mode, and pass through `studySchema`. Parsing succeeds; `integrateSources()` generates **82 negative direct-PAR substeps**. `calculateDay()` still returns an apparently usable DLI map. This is physically invalid input, not a conversion uncertainty.

**Fix:** Share weather validation between all import routes and the engine boundary. Reject diffuse PPFD without total PPFD, diffuse PPFD above total, incomplete PPFD coverage, and invalid interval relationships. Verify rejection after a JSON round trip.

### 3. [P2] Valid large arrays crash all figure-based exports

**Location:** `src/report/figures.js:94–97`.

**Reproduction:** Starting from `defaultStudy()`, set 20 tables per row, 24 rows and 5 m receiver spacing. Both schema validation and `designIssues()` accept the study. `figureSvg()` throws **Maximum call stack size exceeded** at line 94.

The bounds calculation spreads every projected mesh vertex into `Math.min`/`Math.max`, exceeding the JavaScript argument limit. SVG, PNG and the printable methods report all depend on this function. The report handler also lacks the figure handler's error reporting.

**Fix:** Accumulate bounds in a loop instead of spreading an unbounded array. Apply the same rule to other large spreads, release geometry on errors, and surface report-generation failures. Add a regression using an accepted large design.

### 4. [P2] Fit view excludes receiver buffers and field instruments

**Location:** `src/ui/Scene.jsx:41–44,247–248`.

The camera bounds contain only PV/support geometry. Ground cells, receiver buffers, crops and sensors are added afterward without expanding the fitting bounds. Explicit Fit view therefore cannot reliably show the complete experimental area; below-ground instruments can also fall outside a profile fit.

**Reproduction:** With the default study, a plan camera at aspect 1.8 and the implemented 1.15 padding projects the receiver corners to vertical normalized coordinates **±1.0676**, outside the visible ±1 range. Larger perimeter buffers make the exclusion worse.

**Fix:** Fit the display bounds appropriate to the workflow, including actual receiver corners and instrument heights/depths. Continue preserving the existing camera on ordinary edits; expand bounds only for initial framing and explicit refits.

### 5. [P2] Methods tables report the wrong tilt for vertical and pergola racks

**Location:** `src/report/export.js:44–45`.

**Reproduction:** Select vertical or pergola from the default study, then call `methodsRows()`. Both report **25° / ±60°** in “Fixed tilt / tracker limit.” Actual geometry uses 90° for vertical and 0° for pergola. The report also prints backtracking for systems to which it does not apply.

This puts contradictory dimensions in the same publication package: the figures use the effective pose while the methods table uses hidden stored preview values.

**Fix:** Derive publication parameters from the pose contract and rack type. Separate effective fixed tilt, tracker limit and preview pose, and mark inapplicable settings accordingly.

### 6. [P2] Standalone figures and data CSV lose scientific provenance

**Location:** `src/report/figures.js:245`; `src/report/export.js:194–217`.

The SVG contains a title, optional date, geometry/legend and coordinates, but no software version, actual backend, weather identity/hash or model assumptions. PNG rasterizes that SVG and inherits the omissions. Data CSV contains measurements and layout records but no study/date/backend/weather/PAR metadata; its DLI column does not distinguish measured-source from broadband-estimated values.

The separate methods report/CSV supplies much of this context, but the UI permits each artifact to be downloaded independently. Once shared separately, the output no longer carries the information required by the repository's export invariant.

**Fix:** Generate a shared provenance record. Put essential context and the study/result identifier visibly on figures, include machine-readable SVG metadata, and include equivalent CSV metadata or package the data with a mandatory manifest. Explicitly identify estimated DLI.

### 7. [P2] Downloaded weather hashes cannot be verified from saved studies

**Location:** `src/irradiance/weather-service.js:113–136`; weather schema in `src/domain/study.js`.

The SHA-256 is computed over the entire raw response string, but the returned/saved weather contains only normalized day intervals and selected provenance fields. The raw response is discarded, and the schema has no field for it. Normalization clips and transforms the source intervals, so the original hash cannot be reconstructed from the retained data.

The normalized rows do preserve the solver input, which supports rerunning the calculation. The missing piece is the claimed downloaded source snapshot and an independently checkable relationship between that snapshot, its hash and the normalized data. Uploaded files have the same distinction between a source-file hash and retained parsed rows.

**Fix:** Preserve the source text with its hash, and separately hash a documented canonical representation of normalized solver inputs. Retain both through validation and JSON export/import. Label the two hashes clearly.

### 8. [P2] Diffuse tracker quantization can exceed the configured rotation limit

**Location:** `src/domain/geometry.js:40–42`.

Tracker tilt is clamped first and then rounded to a 2° bin without a final constraint. With an 85° limit, backtracking disabled and a low sun in the across-row direction, `getPose(..., true)` returns **86°**. Odd or noninteger limits can likewise be exceeded.

The diffuse solver can therefore use poses outside the user's mechanical envelope and beyond the angle used by clearance validation. Direct visibility uses the constrained pose, so the two integrations use inconsistent limits.

**Fix:** Choose bounded bins or reapply the mechanical limit after quantization; make the cache key represent the final pose. Test positive/negative limits and both tracker types.

## Other improvements

- **Publication sensor identification:** Individual instrument IDs appear in SVG `<title>` elements, but are not visibly drawn. PNG/printed figures show unlabeled dots, making the sensor table difficult to match to the field map. Add optional IDs or a numbered legend with collision handling. Dense profile badges also represent a group at the first instrument's depth; consider grouping profiles by installation height.
- **Rendering efficiency:** `Scene` recreates the renderer, all geometry and controls for every Study change, including typing notes. Preserve the renderer and update only affected objects/materials. This matters as instrument lists and arrays grow.
- **CPU usability:** The browser GPU run finished in 5.2 s for the loaded 5,123-receiver, 577-patch study. The CPU run advanced through diffuse integration over several minutes and was deliberately cancelled at about 41%; cancellation worked. This is not a completed timing comparison. Show elapsed time and a better work estimate, offer an explicit coarse preview, and profile tracker pose/BVH work without silently reducing scientific resolution.
- **Mobile workflow:** At 390 × 844, the page had no horizontal overflow, but the field-sensor controls placed the drawing about 1,804 px below the top. A jump-to-drawing control or collapsible instrument editor would reduce scrolling between controls and placement.
- **Accessibility:** Receiver hover information has no keyboard equivalent, and the canvas is not keyboard focusable. Add a keyboard-accessible receiver/instrument inspector and explicit selected states for projection/layer buttons. Test focus order and screen-reader announcements.
- **CI:** The workflow runs on pushes to main and manual dispatch only. Add pull-request verification so regressions are caught before merging, keeping deployment restricted to main.
- **Scientific release gates:** Independent sky/source-weight, full daily-energy and field validation remain necessary. Add convergence studies and automated real-device GPU/CPU cell-by-cell parity, including device loss, cold/warm caches and storage failures. The successful GPU smoke run does not establish parity.

## Verification and limits

- `npm test`: **38 passed**, no failures.
- `npm run build`: passed; Vite reported a chunk above 500 kB before compression.
- `npm run archive:verify`: **480 archived files checked, zero differences**.
- `npm run validate:radiance`: **45,990 rays, nine cases, zero visibility mismatches**; the shared-weight irradiance differences were zero. This checks occlusion against the same geometry and weights, not independently derived sky or daily-energy physics. The generated validation timestamp was refreshed.
- Real in-app browser: inspected the module, weather, irradiance, field-sensor and publication workflows; completed a WebGPU daily calculation; reproduced the negative-depth entry bug; verified cancellation and restored changed input values. The existing loaded weather was used; this pass did not establish a fresh live weather-download validation.
- Invoked methods HTML and PNG export without reported browser errors. The report showed its download confirmation. This was a generation smoke test, not a page-by-page print-layout or downloaded-PNG inspection.
- Responsive check: 390 × 844, followed by restoration of the normal viewport. No Safari/Firefox or physical mobile-device matrix was run.
- Additional Node reproductions verified invalid JSON PPFD, large-array SVG failure, camera clipping, effective-tilt reporting, missing visible sensor labels and tracker-limit overshoot.

Recommended repair order: numeric editing and shared weather validation first; export robustness and truthful publication parameters second; camera framing, provenance preservation and bounded tracker bins next. Address the scientific release gates before describing the application as validated for publication use.
