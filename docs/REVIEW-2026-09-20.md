# Project review — 20 September 2026

Reviewed commit **e549b7a**, application version **0.4.1**. The working tree was clean at the start. This review covers the active implementation, tests, validation harnesses, build configuration, deployment and documentation; the frozen archive was checked for integrity and left unchanged. Application code and dependencies were not modified during this review. The findings below describe that historical baseline; see [the subsequent implementation report](REVIEW-FIXES-2026-09-20.md) for fixes and remaining external validation.

The shared geometry, validated Study model, worker isolation, weather provenance and export architecture provide a sound foundation. The verification suite passes, including the installed Radiance comparisons and real-browser CPU/WebGPU comparisons. Nevertheless, targeted edge cases exposed eight defects or validation gaps. The most urgent concern lost edits during weather imports, silently misinterpreted timestamps, and the development-server dependency.

**Tracking behavior is implemented:** the irradiance engine derives single- and dual-axis poses from the sun throughout the day, rebuilds moving occluders for direct substeps, and aggregates diffuse visibility by quantized pose (2° by default). The design preview is a reference pose, not an animation of the daily calculation. The current racking defaults implement the requested hemisphere/east–west-facing behavior; R5 identifies a remaining site-import route that bypasses the fixed-tilt hemisphere update.

Priorities: **P1** should be addressed before the next release or affected development use; **P2** should be scheduled next. Reproduction claims distinguish executed probes from code inspection. Performance measurements are local observations, not cross-device guarantees.

## Findings

### R1 — P1: Finishing a weather upload can overwrite newer project edits

**Location:** [src/main.jsx](../src/main.jsx), lines 709–722.

`uploadWeather()` captures `s`, awaits file reading and parsing, then replaces the current study with a copy of that older snapshot. The rest of the editor remains available. The handler has neither a request identity nor a check that the current project, date and period still match the upload. Consequently, edits made during parsing are lost. Opening another project or starting another upload while parsing also creates an overwrite risk; those additional sequences were identified by inspection rather than exercised.

**Executed reproduction:** Mount the real App in JSDOM with a deferred `file.text()`, start a weather upload, change module width from 1.134 m to 1.5 m, then resolve a valid 24-interval CSV. The saved width changes from **1.5 back to 1.134**, and the UI reports a successful upload.

**Recommended change:** Give each import a request token and capture its project/date/period context. At completion, merge weather and eligible site changes into the latest compatible study. Discard cancelled, superseded or context-mismatched imports. Share the lifecycle rules already used by automatic weather downloads.

**Regression:** Deferred upload followed by geometry editing, date changes, project replacement and a second upload. Verify that the latest edits survive and obsolete data never becomes the active weather.

### R2 — P1: CSV accepts timezone-qualified timestamps and treats them as local time

**Location:** [src/irradiance/weather.js](../src/irradiance/weather.js), lines 45–55.

The timezone rejection recognizes `Z` and offsets such as `+00:00`, but misses `+0000`, `-0700` and `+00`. The subsequent time regex is not anchored to the end of the timestamp and ignores those suffixes, as well as arbitrary trailing text. The resulting local time feeds solar position and moving-shadow calculations.

**Executed reproduction:** Complete 24-row CSVs ending each timestamp in `+0000`, `-0700`, `+00` or `garbage` are accepted. Equivalent `Z` and `+00:00` files are rejected as intended. For example, `2026-06-21T12:00+0000` becomes 12:00 local standard time, which is seven hours later than the represented instant at UTC−7. Some weather consistency checks may catch particular resulting datasets, but the timestamp parser itself silently accepts the wrong semantics.

**Recommended change:** Validate the entire timestamp against a documented local-standard-time grammar, including valid hour/minute fields. Consistently reject timezone suffixes, or explicitly implement conversion and date-boundary handling. Use the same parser for date-qualified and time-only CSV records.

**Regression:** All supported and rejected timezone forms, trailing characters, malformed minutes/hours, fractional offsets and midnight/date boundaries. Include diffuse-only weather so unrelated DNI/night checks cannot conceal parser errors.

### R3 — P1: The pinned Vite version has published high-severity advisories

**Location:** [package.json](../package.json), `devDependencies.vite`; [vite.config.js](../vite.config.js), `server.fs.deny`.

The live npm audit reports **one vulnerable dependency, rated high**, covering five advisories for pinned Vite **7.1.12**. They include development-server filesystem-deny bypass and arbitrary file-read issues. The repository expressly denies access to `.git`, the archive and `.env` files, so these protections should not depend on an affected server version. The audit proposes **7.3.6** as a non-major upgrade. See the primary [Vite filesystem-deny advisory](https://github.com/vitejs/vite/security/advisories/GHSA-v2wj-q39q-566r) and [Vite WebSocket file-read advisory](https://github.com/vitejs/vite/security/advisories/GHSA-p9ff-h696-f583).

This is a **development-server finding**. The normal dev command binds to loopback, and the GitHub Pages deployment serves built static files rather than Vite. The audit did not report a production dependency vulnerability. No exploit attempt was made.

**Recommended change:** Upgrade the exact Vite pin and lockfile to a compatible patched release, then rerun worker warm-up, development navigation, build and browser checks. Add a recurring dependency audit or dependency-update workflow so pins remain deliberate without remaining indefinitely vulnerable.

### R4 — P2: Zero measured DLI crashes the DLI color scale and dependent exports

**Location:** [src/report/figures.js](../src/report/figures.js), lines 18–35; [src/project/package.js](../src/project/package.js), lines 210–221.

`heatColor(0, 0)` divides by zero, produces `NaN`, then attempts `.map()` on an undefined color stop. A complete weather record with measured PPFD and diffuse PPFD equal to zero is accepted by current validation. The solver can return positive broadband irradiation alongside zero DLI. This reaches the zero-range color scale.

**Executed reproduction:** Solve a small CPU study using a complete illustrative broadband day with PPFD = diffuse PPFD = 0 in every interval. The result has `openWh = 7222.856271000001` and `openDli = 0`. Generating its DLI SVG throws **“Cannot read properties of undefined (reading 'map')”**. The interactive map uses the same helper; project packages include a DLI figure automatically, so this also blocks normal package generation with such results.

**Recommended change:** Define a finite zero-range scale, color and legend. Guard non-finite values at the shared color helper. If inconsistent measured PAR/broadband data should generate a scientific warning, implement that separately; the renderer should still handle zero safely.

**Regression:** Zero measured PPFD through solve, map, SVG, PNG, methods report and project package.

### R5 — P2: Weather metadata imports bypass hemisphere-aware fixed-tilt defaults

**Location:** [src/main.jsx](../src/main.jsx), lines 715–717; compare the shared latitude-update behavior in [src/domain/study.js](../src/domain/study.js).

Manual latitude changes and place selection use the orientation-aware update path. EPW/TMY3 uploads instead merge `parsed.site` directly into the study. Moving a standard northern fixed-tilt study to a southern location through a weather import therefore leaves the panels facing south.

**Executed reproduction:** Parse EPW metadata for latitude −33°, longitude 151°, UTC+10 and apply the handler's exact schema/merge expression to a default fixed system. The result has **latitude −33° and azimuth 180°**; the requested default is 0° at that location.

**Recommended change:** Apply imported site metadata atomically through the same orientation-aware helper used for place/manual changes, while preserving custom bearings and the explicit preservation policy for whole-project imports. Combine this with R1's current-state merge.

**Regression:** EPW and TMY3 hemisphere transitions in both directions, unchanged hemispheres, custom fixed bearings, tracker/vertical bearings and whole-project imports.

### R6 — P2: Oversized input can exhaust display/grid work before the solver limit applies

**Location:** [src/domain/receiver-grid.js](../src/domain/receiver-grid.js), lines 27–64 and 100–105; [src/domain/study.js](../src/domain/study.js), lines 539–540; grid construction in [src/ui/Scene.jsx](../src/ui/Scene.jsx).

Module gap intentionally accepts any finite nonnegative distance. The 20,000-receiver limit is checked only after constructing the receiver specification, including its full `yEdges` array. Display and layout paths also consume this grid while the design is invalid. `gridSpacingLabel()` spreads every row height into `Math.min`/`Math.max`, creating another unbounded operation.

**Executed reproduction:** With an otherwise default study and module gap 10,000 m, schema parsing succeeds and the derived grid has **100,020 × 11,289 = 1,129,125,780 cells**. The solver warning exists, but only after grid construction. At gap 200,000 m, the specification has 225,039 rows and `gridSpacingLabel()` throws **“Maximum call stack size exceeded”**. These deliberately extreme inputs test robustness; no billion-cell geometry or deliberate out-of-memory browser render was attempted.

**Recommended change:** Estimate grid counts with scalar arithmetic before allocating edges, cells or display lines. Return an editable invalid-design state with a clear budget warning. Bound display geometry independently of solver geometry, and replace unbounded argument spreads with loops. Preserve the user's ability to edit a large gap back to a valid value.

**Regression:** Very large finite gaps, footprints, buffers and high-resolution grids through schema, controls, field normalization, scene and import paths. Assert bounded work and an actionable warning.

### R7 — P2: Editing module construction can leave the visible module unchanged

**Location:** [src/ui/Scene.jsx](../src/ui/Scene.jsx), lines 90–123 and 380–396; [src/domain/geometry.js](../src/domain/geometry.js), lines 89–119.

The scene only rebuilds module geometry/materials when `structureKey` changes. That key includes external dimensions and module spacing, but omits bifacial construction, cell counts, cell gaps and frame margin. Those omitted fields determine the texture created by `buildGeometry()`. Other scene keys do not refresh that texture either.

**Code-inspection finding:** Change bifacial construction or the cell layout while remaining in the module view (or relevant vertical view). The existing material/texture is retained until a separate structural change or remount. This is a stale visualization issue: the numerical analysis key includes module inputs, so this finding does not establish stale solver results.

**Recommended change:** Track a separate material/optics identity and refresh shared module materials/textures when it changes, preserving camera state. Avoid rebuilding all hardware solely to update appearance. Also reconcile the fixed decorative cell grid with user-defined cell counts.

**Regression:** Change construction, cell count and gaps without navigating away, and verify the visible texture updates while camera framing remains stable.

### R8 — P2: Saved-result validation accepts impossible received energy

**Location:** [src/project/results.js](../src/project/results.js), lines 30–80.

Saved cell energy is bounded only by a large generic numeric maximum. Relative sunlight is checked against a ratio clamped to 100%, so a value greater than open-field irradiation remains valid if its sunlight is 100%. Source totals and measured/estimated status are also not independently reconciled to the retained weather. Checksums and input identities are useful, but they do not establish physical consistency of the supplied output.

**Executed reproduction:** Clone a valid daily result, set every cell's `wh` to **twice `openWh`**, and set cell/summary sunlight to 100% and shade to 0%. Retain the correct input key, study hash, weather identity, coordinates and DLI. `validateResult()` accepts it. This demonstrates an import-validation gap, not that the current solver generated excess energy. Package checksums catch accidental file changes unless recomputed; legacy result JSON also reaches this validation boundary.

**Recommended change:** Enforce receiver irradiation and DLI limits relative to their open-field references with explicit numerical tolerances. Reconcile open-field totals and measured/estimated status from retained source data without retracing visibility. Apply equivalent checks to daily, monthly, period and resumable results.

**Regression:** Over-reference energy/DLI, tampered source totals and status, zero-source days and valid floating-point tolerances.

## Other improvements and coverage gaps

- **CSV formula handling:** `report/export.js:42–55` escapes text beginning with `=`, `+`, `@`, tab or carriage return, but not `-`. A direct helper probe leaves the string `-1+1` unprefixed. Expand spreadsheet-import tests and distinguish text metadata from genuine negative numeric coordinates before changing escaping. No spreadsheet execution or exploit was tested.
- **Input/import boundaries:** Add file-size and record-count budgets before large weather parsing, and cancellation/context ownership for every asynchronous import. Keep schema errors visible without discarding current work.
- **Regression selection:** The existing UI test suite did not expose R1 or the import-specific orientation path. Add deferred-I/O and route-equivalence tests; increase real-browser coverage for material refresh, zero color scales and invalid-design recovery.
- **CI:** The Pages workflow verifies archive integrity, tests and build. Add the existing formatting check and a dependency-audit policy. Add a CPU browser smoke test; run real GPU/device-loss checks on an appropriate supported runner. Keep missing Radiance explicitly reported as unvalidated rather than counted as a passing oracle run.
- **Scientific validation:** CPU/GPU agreement and Radiance first-hit agreement are strong implementation checks, but both browser backends share solar/sky/integration logic. Independent solar-position, Perez sky, whole-day irradiation and measured/estimated DLI comparisons remain necessary. Extend convergence studies to southern latitudes, low-sun conditions, dense/large arrays, transmission and within-cell sampling; no universal accuracy threshold is established by current tests.
- **Reproducibility:** Preserve exact dependency pins, retained weather and actual-backend provenance. Introduce an explicit numerical-model/cache revision or build commit in future numerical releases so old cached visibility and result packages cannot be mistaken for outputs of a changed algorithm.
- **Usability/resilience:** Consider a clear unsaved-field-layout indicator and explicit export reminder under the current no-field-autosave policy. Add context-loss recovery and Safari/Firefox/mobile checks; this review's actual GPU browser checks were Chromium-only. These are improvement opportunities, not reproduced regressions.

## Suggested implementation order

1. Fix the asynchronous upload lifecycle and shared site/orientation update, then harden timestamp parsing. Add focused regressions for each import route.
2. Upgrade Vite and verify development workers, build and browser behavior.
3. Fix zero-range DLI rendering, early grid budgets, module-material refresh and saved-result physical checks.
4. Optimize annual parsing, stable analysis identities and period engine reuse; benchmark representative annual fixed and tracking studies before and after.
5. Introduce tiled transmission and bounded display instancing, then optimize crop summaries, cache eviction and persistence/export work.
6. Expand independent scientific and cross-browser validation before making broader accuracy or performance claims.
